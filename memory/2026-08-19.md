# 2026-08-19

## Durable editorial learnings

- `Discovery` nesmí vycházet z mainstreamového článku nebo přejmenovaného launch coverage. Nejdřív musí být vlastní čerstvý signál, pak reality check, potom saturace check.
- Téma staré několik dní až týdnů už není automaticky `Discovery`; bez nového originálního zdroje nebo nového triggeru patří max do `Current Demand` nebo `Drop`.
- `9to5Google` a podobná velká média jsou dobrá na saturaci a ověření, ne jako primární zdroj nápadu pro Discovery.
- Před každým `CREATE` musí proběhnout tvrdý `WP duplicity check`; pokud je téma už publikované nebo čerstvě pokryté, je potřeba zvolit nový úhel, `MONITOR`, `UPDATE` nebo `DROP` místo duplicitního článku.
- Publikovaný článek je `READ-ONLY`. Po publikaci se na něj nesmí sahat, přepisovat ho ani mazat bez výslovného nového pokynu od Romana nebo Toma.
- U SamsungMagazine fungují lépe praktické, uživatelské úhly než recyklace novinek. Slabé jsou články, které jen opakují už vydané věci nebo tlačí téma bez jasného přínosu pro čtenáře.
- U watch témat je důležité mluvit o konkrétní funkci a jejím dopadu, ne motat do článku zbytečné srovnání, které nemá pro danou funkci smysl.

## Durable workflow updates

- Finální denní workflow pro AndroidMagazine je V6.5: broad sourcing -> source coverage audit -> discovery hunt -> candidate universe -> normalization/clustering -> reality check -> information age -> saturation -> WP/cannibalization -> unique value -> demand/predictive/commercial intelligence -> scoring -> ranking -> counterfactual top 1/top 3 -> marginal portfolio value -> final portfolio -> author/timing -> actionable brief -> publish -> measure -> learn.
- `Discovery` se klasifikuje jen když existuje skutečný information advantage; samotná čerstvá mainstream coverage nestačí.
- `Source Coverage Audit` musí být explicitní a má ukazovat, které source family byly checked, unavailable nebo bez relevantního signálu.
- GitHub je trvalý early-signal sensor, ale nemá garantované místo v portfoliu; konkuruje GSC, Trends, News, WP a dalším zdrojům na stejné úrovni.
- GitHub monitor je read-only, používá `GITHUB_TOKEN`, delta sync, lokální raw storage, semantic/event clustering a `LOW / MEDIUM / HIGH` editorial potential.
- `LOW` GitHub clustery jdou do lokálního watchlistu a nepouští se běžně do LLM; re-eval probíhá jen při novém relevantním triggeru.
- `MEDIUM` a `HIGH` GitHub clustery musí mít `user_impact_reason` a `user_impact_confidence`; `HIGH` znamená jasný nebo velmi pravděpodobný user-facing dopad, ne jen technickou důležitost.
- Watchlist promotion není CREATE; i promovaný cluster musí projít celým V6.5 funnel.
- Google News se má brát jako samostatná News Intelligence vrstva pro first_seen/saturation/performance, ne jako důkaz Discovery.

## Durable implementation state

- Multi-Source Orchestrator je implementovaný jako společná local-first vrstva nad napojenými zdroji `GSC`, `GA4`, `WordPress`, `GitHub` a `Trends`; `Google News`, `Reddit`, `X`, `YouTube` a `AdSense` zůstávají zatím `NOT IMPLEMENTED`.
- Orchestrátor používá jeden normalized signal model, cross-source clustering, globální ranking, counterfactual top 1 / top 3 test a marginal portfolio value; běží zatím jen v `TEST MODE`, ne na ranním cronu.
- GitHub watchlist persistence je implementovaná do lokální DB: re-eval změny se zapisují persistentně s `previous_status`, `new_status`, `triggering_signal`, `supporting_source_families`, `promotion_reason`, `reassessed_at` a `confidence`.
- GitHub watchlist re-evaluation je trigger-driven a nepřepočítává LOW clustery bez nového relevantního signálu; `PROMOTION != CREATE` pořád platí.
- `LOW` GitHub clustery se ukládají do watchlistu a mimo trigger se neposílají do LLM ani do editorial shortlistu.
- `user_impact_reason` a `user_impact_confidence` jsou povinné pro `MEDIUM` a `HIGH` GitHub clustery.
- Structured Trends store je samostatná lokální SQLite vrstva a orchestrátor už nemá číst jen hotový editorial report; ukládá strukturované trend signály a pracuje s nimi jako s cache/seed vrstvou.
- Trend signály v lokální cache mají minimálně `trend_id`, `query`, `entity`, `topic_cluster`, `geo`, `first_seen_at`, `latest_seen_at`, `trend_value`, `previous_value`, `velocity`, `acceleration`, `peak`, `source` a `fetched_at`, přičemž neexistující metriky se značí `UNAVAILABLE`.

## Durable production readiness

- Cross-source watchlist re-evaluation je persistentní: pokud nový cross-source trigger povýší GitHub LOW/MEDIUM cluster, zápis se ukládá do lokální DB a přežije restart orchestrace.
- Multi-Source Orchestrator prošel posledním production-readiness testem před cronem: cross-source promotion, persistence after restart, Candidate Universe re-entry i production data unchanged vyšly `PASS`.
- Multi-Source Orchestrator je označen jako `PRODUCTION READY`, ale ranní cron se zatím nezapíná automaticky bez dalšího pokynu.

## Durable production execution

- Ranní Multi-Source Orchestrator workflow je zapnutý v `PRODUCTION ACTIVE` režimu a běží ve supervised režimu bez automatické publikace článků.
- Produkční pořadí kroků je fixně: `SOURCE DELTA SYNC -> LOCAL STORES -> NORMALIZATION -> CROSS-SOURCE CLUSTERING -> WATCHLIST RE-EVALUATION -> CANDIDATE UNIVERSE -> V6.5 FUNNEL -> GLOBAL RANKING -> FINAL PORTFOLIO -> MORNING REPORT`.
- Produkční běhy musí logovat `source coverage`, `API calls`, `LLM calls`, `raw/normalized signal counts`, `cross-source clusters`, `watchlist promotions`, `qualified candidates`, `TOP 10`, `final portfolio` a `errors/fallbacks`.
- Pokud zdroj selže, workflow pokračuje s dostupnými zdroji a označí zdroj jako `UNAVAILABLE`; není-li chyba kritická, celý běh se nezastavuje.
- `Google News`, `Reddit`, `X`, `YouTube / community` a `AdSense` zůstávají v produkčním workflow stále `NOT IMPLEMENTED`; orchestrátor je nesmí předstírat jako hotové.

## Durable ranking audit

- První produkční výběr ukázal, že rankování je obhajitelné hlavně v top 1-4, ale od pozic 5-8 je `RANKING UNCERTAIN`.
- Výběr byl příliš silně ovlivněn historickou `GSC/GA4` poptávkou a málo `novelty`, `momentum` a `time advantage`; žádný skutečný Discovery kandidát se do finálního portfolia nedostal.
- `GitHub` se v prvním produkčním portfoliu neprosadil a v top výběru nebyl rozhodující faktor.
- Audit identifikoval jako slabé/filler kandidáty zejména `play store` a `rcs`; naopak `pixel 11`, `android 16`, `android 17`, `jak vypnout ai funkce na` a `google pixely dostaly unikatni aplikaci` byly datově obhajitelnější.
- Kategorie bias je stále přítomný: finální portfolio se výrazně naklánělo do `CURRENT DEMAND / TREND` a jen část kandidátů měla skutečně silný současný uživatelský impuls.
- Kandidáti nesmí být jen obecné entity nebo query; pro finální výběr se musí převádět na konkrétní editorial opportunity ve formátu `WHAT HAPPENED / WHAT USERS WANT TO KNOW / WHY NOW / WHAT CAN WE ADD`.
- Pro další tuning je potřeba hlídat, aby ranking nebyl nepřiměřeně ovlivněný historickou `GSC/GA4` poptávkou na úkor novosti, momentum a time advantage.

## Durable ranking architecture update

- `Ranking architecture` má být lane-based, ne jeden globální score pro všechny kandidáty.
- Každý kandidát se má nejdřív hodnotit uvnitř své lane: `BREAKING / CURRENT NEWS`, `DISCOVERY / PREDICTIVE`, `CURRENT DEMAND / TREND`, `SEO / SEARCH OPPORTUNITY`, `UPDATE / REWRITE`.
- `Final Portfolio` má být dynamický podle kvality kandidátů v jednotlivých lanes, ne podle pevné kvóty.
- `Discovery` nesmí být penalizované jen proto, že nemá historickou `GSC/GA4` poptávku; naopak silné evergreen SEO nesmí vytlačit čerstvou opportunity jen kvůli starší demand.
- `first_seen_by_lisa` se nesmí plést s historickým WP/GSC datem; je potřeba rozlišovat `information_first_public_at`, `source_record_first_seen_at`, `lisa_first_seen_at` a `story_first_seen_at`.
- `GitHub evidence propagation` je kritické místo: persistentní GitHub/watchlist evidence se musí propisovat až do normalized signals, cross-source clusters, candidate evidence a lane scoringu. `UNAVAILABLE` kvůli technické ztrátě dat není validní stav.
- Při auditu se ukázalo, že `GitHub` evidence byla v top kandidátech často `UNAVAILABLE`, i když GitHub monitor existuje; to je potřeba dál fixovat jako data lineage bug.
